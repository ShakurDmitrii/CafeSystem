## 1. Назначение документа

Документ фиксирует полный план проверки backend CafeHelp, чтобы работа могла выполняться последовательно, а важные сценарии не потерялись между отдельными задачами.

Основные цели проверки:

- убедиться, что критические операции с заказами, оплатами, складами, сменами и долгами выполняются корректно и атомарно;
- проверить разграничение доступа между `OWNER`, `WORKER`, внутренними сервисами и неавторизованными пользователями;
- сделать запуск приложения и базы данных воспроизводимым;
- определить минимальный набор автоматических тестов для безопасного дальнейшего развития;
- проверить устойчивость интеграций с PostgreSQL, налоговым контуром, MinIO, VK-ботом и Python-сервисом;
- сформировать реестр дефектов и улучшений с приоритетами.

На данном этапе **не выполняется оценка качества прогнозных и генеративных алгоритмов PyModule**. Для Python-сервиса проверяются только API-контракты, авторизация, доступность, тайм-ауты, обработка ошибок и поведение Java backend при недоступности сервиса.

## 2. Текущий контур backend

По результатам первичного просмотра проект содержит:

| Компонент | Назначение |
|---|---|
| Spring Boot 3.5.7 / Java 21 | Основное backend-приложение |
| Spring Security + JWT | Авторизация и роли `OWNER` / `WORKER` |
| jOOQ | Доступ к основной базе данных |
| PostgreSQL | Данные продаж, меню, складов, смен, сотрудников и клиентов |
| Отдельная PostgreSQL tax DB | Налоговые чеки и связанные операции |
| SQL migrations + `DatabaseSchemaInitializer` | Обновление структуры базы данных при старте |
| MinIO | Хранение загружаемых файлов и изображений |
| Python / ML service | Аналитика, прогнозы и ML-функции |
| VK bot | Привязка клиента и получение информации о заказах |
| Tax outbox и dispatch-контур | Надёжная передача данных о чеках |
| OpenAPI / Swagger UI | Просмотр и ручная проверка API |

Ориентировочный объём Java backend на момент просмотра:

- 24 REST-контроллера;
- около 150 HTTP endpoint;
- 38 сервисных классов;
- 72 DTO;
- 12 миграций основной БД и 1 миграция tax DB;
- 1 минимальный `contextLoads`-тест и вспомогательный `TestRunner` без проверочных утверждений.

## 4. Предварительные находки

Это результаты первичного просмотра, а не окончательный аудит. Каждую находку необходимо подтвердить отдельным воспроизводимым тестом.

### 4.1. P0 — складские endpoint разрешены без авторизации

**Статус на 31 июля 2026 года:** исправлено и покрыто integration-тестами.
Анонимный доступ запрещён; безопасные операции чтения доступны `WORKER` и
`OWNER`, изменения и инвентаризация — только `OWNER`.

В `SecurityConfig` пути `/warehouses` и `/warehouses/**` имеют `permitAll()`. При этом `WareHouseController` содержит не только чтение, но и:

- создание, изменение и удаление склада;
- назначение главного склада;
- добавление товаров;
- прямую корректировку остатков продуктов и заготовок;
- применение фактических остатков инвентаризации.

**Риск:** любой клиент, имеющий сетевой доступ к backend, потенциально может изменять складские данные без JWT.

**Что сделать при проверке:**

1. Вызвать каждый складской endpoint без токена.
2. Повторить с токенами `WORKER` и `OWNER`.
3. Согласовать матрицу прав.
4. После исправления закрепить матрицу автоматическими security-тестами.

### 4.2. P0 — оплата заказа и списание остатков могут рассинхронизироваться

**Статус на 31 июля 2026 года:** исправлено и покрыто integration-тестами.

Зафиксировано бизнес-правило:

- нехватка продукта или заготовки не отменяет заказ и оплату;
- со склада списывается всё доступное количество без ухода в отрицательный остаток;
- недостающая часть рассчитывается по снимку смены, движениям и продажам и отображается в инвентаризационном отчёте как `shortageQty`;
- ошибка БД или другая техническая ошибка откатывает заказ и позиции целиком;
- повторная или параллельная отметка одного заказа оплаченным не приводит к повторному списанию.

До исправления в `OrderService` присутствовали опасные последовательности:

- `createOrder` не отмечен `@Transactional`, хотя создаёт заказ, позиции заказа и может списывать остатки;
- ошибка складского списания при создании оплаченного заказа перехватывается и только выводится в лог;
- `updateOrderPayment` сначала помечает заказ оплаченным, а ошибку последующего списания также подавляет;
- при добавлении блюда в оплаченный заказ складское списание и запись позиции не образуют единый гарантированный сценарий.

**Риск:** заказ может считаться оплаченным, но продукты не будут списаны; также возможны частично созданные заказы и некорректные остатки.

**Что сделать при проверке:**

1. Создать оплаченный заказ при достаточном остатке.
2. Повторить при недостаточном остатке.
3. Искусственно вызвать ошибку после создания заказа, но до записи всех позиций.
4. Проверить повторную отправку одинакового запроса.
5. Проверить параллельную оплату одного заказа.
6. Зафиксировать ожидаемое правило: либо вся операция успешна, либо все изменения откатываются.

### 4.3. P0 — текущий набор миграций не даёт надёжной воспроизводимости

**Статус на 31 июля 2026 года:** основной блок исправлен и закреплён
контейнерным smoke-тестом. Осталось удалить дублирование между миграциями и
`DatabaseSchemaInitializer`.

Первичный запуск тестов остановился на несовпадении checksum для уже применённой миграции:

`db/migrations/2026-01-01_sales_baseline.sql`.

Дополнительно в `docs/database-migrations.md` уже отмечено, что текущий набор миграций не создаёт всю основную схему с нуля и предполагает наличие legacy-схемы `sales`.

При старте также запускается большой `DatabaseSchemaInitializer`, который отдельно выполняет DDL, создаёт ограничения и меняет данные. В результате структура БД формируется одновременно двумя механизмами.

**Риск:** новая среда может не подняться с нуля, а разные установки могут получить различающиеся схемы.

**Что сделать при проверке:**

1. Зафиксировать эталонную структуру рабочей базы.
2. Не изменять уже применённые миграции; все корректировки оформлять новыми файлами.
3. Поднять пустую основную БД и пустую tax DB.
4. Применить только версионируемые миграции.
5. Сравнить полученную схему с эталоном.
6. Перенести изменения из `DatabaseSchemaInitializer` в миграции и оставить один механизм управления схемой.

### 4.4. P0/P1 — VK API может работать без секретного токена

**Статус на 31 июля 2026 года:** исправлено. При отсутствии секрета API
возвращает `503`, при неверном токене — `401`; сравнение выполняется постоянным
по времени способом. Удалена ошибочная связь bot token с `VK_GROUP_TOKEN`.

Пути `/api/vk-bot/**` разрешены без JWT. Контроллер выполняет собственную проверку заголовка, но если настройка токена пустая, проверка полностью пропускается.

Кроме того, контроллер читает `vk.bot.api-token`, а в `application.properties` это свойство связано с `VK_GROUP_TOKEN`, хотя в Docker отдельно передаётся `VK_BOT_API_TOKEN`.

**Риск:** при пустой или неверно связанной настройке внешнему клиенту могут стать доступны операции привязки и сведения о заказах клиента.

**Что сделать при проверке:**

1. Запустить backend без VK-токенов и проверить все `/api/vk-bot/**`.
2. Проверить запуск с `VK_BOT_API_TOKEN`, но без `VK_GROUP_TOKEN`.
3. Убедиться, что приложение не стартует либо закрывает API при отсутствии обязательного секрета.
4. Использовать постоянное по времени сравнение секретов и добавить ограничение частоты запросов.

### 4.5. P1 — секреты и пароли частично находятся в конфигурации проекта

В `application.properties`, `docker-compose.yml` и настройке jOOQ присутствуют фиксированные пароли PostgreSQL и стандартные данные MinIO. JWT и internal service token в Docker уже сделаны обязательными, но локальная конфигурация остаётся неоднородной.

**Риск:** повторное использование тестовых значений в доступной среде, случайное раскрытие секретов и сложная ротация.

**Что сделать при проверке:**

- составить перечень всех секретов;
- вынести их в переменные окружения или secret storage;
- убрать реальные ИНН, пароли и ключи из общей конфигурации;
- добавить безопасный `.env.example` без значений;
- проверить, что production-профиль не запускается с тестовыми значениями;
- после изменения настроек выполнить ротацию ранее использованных секретов.

### 4.6. P1 — внутренний service token получает полные права `OWNER`

`ServiceTokenAuthenticationFilter` создаёт аутентификацию с ролью `OWNER`. Это даёт внутреннему токену доступ не только к нужным интеграционным endpoint, но потенциально ко всему административному API.

**Что сделать при проверке:**

- составить список endpoint, которые действительно нужны PyModule и другим сервисам;
- ввести отдельную роль, например `INTERNAL_SERVICE`;
- ограничить токен конкретными маршрутами;
- проверить отсутствие доступа к сотрудникам, аккаунтам, складам и административным операциям;
- предусмотреть ротацию токена и аудит его использования.

### 4.7. P1 — деактивация пользователя не отзывает ранее выданный JWT

При логине проверяется активность аккаунта, но на последующих запросах JWT принимается без повторной проверки текущего статуса и роли пользователя в БД. Срок жизни токена по умолчанию — 8 часов.

**Риск:** деактивированный сотрудник или пользователь с изменённой ролью сохраняет старые права до истечения токена.

**Что сделать при проверке:**

1. Авторизовать пользователя и сохранить токен.
2. Деактивировать аккаунт.
3. Проверить доступ старым токеном.
4. Изменить роль и повторить проверку.
5. Выбрать механизм отзыва: короткий access token, token version, denylist либо проверка аккаунта для чувствительных операций.

### 4.8. P1 — публичный bootstrap требует проверки гонки и условий отключения

`/api/auth/bootstrap` публичен и закрывается после появления первого аккаунта. Проверка количества аккаунтов и создание владельца не образуют явно защищённую от параллельного выполнения операцию.

**Что сделать при проверке:**

- отправить несколько параллельных bootstrap-запросов в пустую БД;
- проверить, что создаётся только один владелец;
- проверить невозможность повторного bootstrap после создания аккаунта;
- определить безопасный способ первичной инициализации: одноразовый setup token, CLI-команда или обязательный deployment secret.

### 4.9. P1 — нет единого контракта валидации и ошибок

Зависимость Bean Validation подключена, но в просмотренных DTO и контроллерах не используются `@Valid`, `@NotNull`, `@NotBlank`, `@Positive` и аналогичные ограничения. Проверки выполняются вручную и различаются между endpoint.

Исключения обрабатываются неодинаково:

- часть endpoint возвращает `null`;
- часть — строку;
- часть — `Map` с ключом `message` или `error`;
- часть преобразует любую ошибку в HTTP 500;
- местами наружу возвращается `e.getMessage()`, что может раскрыть внутренние детали;
- глобальный обработчик есть только для ошибок Python-сервиса.

**Что сделать при проверке:**

- определить единый формат ошибки;
- добавить валидацию входных DTO;
- ввести глобальный обработчик ожидаемых ошибок;
- разделить `400`, `401`, `403`, `404`, `409`, `422`, `500`, `502/503`;
- проверить отсутствие stack trace, SQL и внутренних URL в ответах.

Рекомендуемый формат:

```json
{
  "code": "INSUFFICIENT_STOCK",
  "message": "Недостаточно товара на складе",
  "fieldErrors": [],
  "traceId": "..."
}
```

### 4.10. P1 — автоматическое тестовое покрытие практически отсутствует

Текущий тестовый набор содержит только загрузку Spring-контекста. `TestRunner` печатает данные в консоль, не содержит утверждений и запускается вместе с тестовым контекстом, из-за чего тест зависит от состояния БД.

**Что сделать при проверке:**

- заменить консольные проверки на изолированные JUnit-тесты;
- не использовать рабочую или разработческую БД;
- добавить Testcontainers для PostgreSQL;
- построить тесты по рискам, начиная с безопасности и денежных/складских операций;
- обеспечить один воспроизводимый запуск всех тестов командой Gradle.

### 4.11. P1 — выплаты зарплаты перенесены в backend

**Статус на 7 августа 2026 года: исправлено и покрыто интеграционными тестами.**

Ставка фиксируется в отдельном начислении при закрытии смены, а выплаты и их отмены хранятся неизменяемыми проводками PostgreSQL. Общий остаток больше не зависит от конкретного браузера и изменения будущей ставки не пересчитывают уже закрытые смены.

Операции доступны только активному `OWNER`, содержат автора и серверное время, сериализуются по сотруднику и требуют ключ идемпотентности. Интерфейс удаляет устаревший ключ `salaryPayments` только после успешной загрузки серверных остатков. Автоматического импорта локальной истории нет: новый доверенный журнал начинается со смен, впервые закрытых после миграции.

Решение и контракт описаны в `docs/adr/0001-server-payroll-ledger.md` и `docs/api/employee-payroll.openapi.yaml`.

### 4.12. P2 — закрытие и изменение смены требуют проверки транзакционности

**Статус на 31.07.2026: исправлено и покрыто интеграционными тестами.**

`closeShift` и `updateShift` выполняются транзакционно. Закрытие блокирует строку смены до фиксации итогов; создание заказа, его оплата и остальные изменяющие операции используют ту же блокировку. Поэтому заказ либо полностью фиксируется до закрытия и попадает в итог, либо получает конфликт закрытой смены.

Зафиксированы правила:

- доход и себестоимость включают только оплаченные и неотменённые заказы;
- неоплаченные и долговые заказы отображаются в Z-отчёте отдельно и не считаются полученной выручкой;
- цена и себестоимость фиксируются в строке заказа и не меняются задним числом после редактирования меню;
- отрицательные и `null`-расходы отклоняются;
- повторное и параллельное закрытие идемпотентно и возвращает первый сохранённый результат;
- общий endpoint изменения смены не принимает от клиента время закрытия и финансовые итоги;
- кассовый интерфейс закрывает смену через `/api/shifts/{id}/close`, а не рассчитывает итог в браузере.

### 4.13. P2 — CORS настроен в нескольких местах

CORS одновременно задаётся в `SecurityConfig`, отдельной конфигурации и аннотациях контроллеров. Разрешён только `http://localhost:3000`.

**Риск:** расхождения между средами, непредсказуемое поведение preflight и ручные изменения при каждом deployment.

**Что сделать:** оставить один конфиг, вынести origins в переменные окружения и добавить тесты для разрешённого и запрещённого origin.

### 4.14. P2 — backend не имеет полноценной эксплуатационной диагностики

В Docker есть healthcheck для PostgreSQL и PyModule, но не для Java backend. Spring Boot Actuator и прикладные метрики не подключены.

**Что сделать:**

- добавить readiness и liveness;
- проверять отдельно доступность основной БД и tax DB;
- добавить метрики ошибок, времени ответа, пула соединений, outbox и внешних интеграций;
- использовать структурированные логи и `traceId`;
- не включать секреты и персональные данные в логи.

### 4.15. Положительные элементы, которые следует сохранить

- stateless-аутентификация и BCrypt для паролей;
- JWT secret обязателен при Docker-запуске;
- сравнение internal service token выполняется постоянным по времени способом;
- в движениях, проводке накладных и части операций уже применяются транзакции;
- tax-контур использует outbox, повторные попытки и `FOR UPDATE SKIP LOCKED`;
- миграционный механизм проверяет checksum и тем самым обнаруживает изменение применённых файлов;
- основная и налоговая базы разделены.

## 5. Общая стратегия проверки

Проверка строится снизу вверх:

1. **Воспроизводимость окружения** — чистый запуск, миграции и тестовые данные.
2. **Безопасность API** — аутентификация, роли и внешние токены.
3. **Контракты API** — входные данные, статусы, ответы и ошибки.
4. **Бизнес-логика** — заказы, оплаты, смены, склад, долги, зарплата.
5. **Интеграции** — tax DB, налоговый провайдер, MinIO, VK и Python.
6. **Конкурентность** — повторные и параллельные операции.
7. **Производительность и наблюдаемость** — время ответа, метрики и диагностика.
8. **Регрессия** — автоматизация критических сценариев в CI.

Для каждого дефекта должны быть:

- воспроизводимый сценарий;
- ожидаемый и фактический результат;
- оценка влияния;
- приоритет;
- предлагаемое исправление;
- автоматический регрессионный тест.

**Статус на 2 августа 2026 года:** выполнено.

Зафиксированы и реализованы правила:

- имя клиента очищается от лишних пробелов, телефон приводится к единому виду; один нормализованный телефон не может принадлежать двум карточкам;
- однофамильцы и клиенты без телефона разрешены, потому что имя само по себе не является надёжным идентификатором;
- долговой заказ требует существующего клиента и обещанную дату оплаты;
- продукты списываются при создании долгового заказа, поскольку блюдо уже произведено; последующее получение денег не выполняет второе складское списание;
- сумма первоначального долга и текущий остаток хранятся отдельно, каждый платёж записывается в `sales.debt_payment` вместе с остатком после операции;
- `POST /api/clients/debts/{orderId}/payments` поддерживает частичную и полную оплату и обязательный ключ идемпотентности; `GET` по тому же пути возвращает историю;
- параллельные платежи блокируют строку заказа, поэтому долг нельзя погасить сверх остатка;
- платёж по долгу после закрытия смены не переписывает историческую выручку Z-отчёта: момент оплаты и момент финансового закрытия смены фиксируются отдельно;
- бизнес-дата рассчитывается в настраиваемой зоне `app.business-zone` (по умолчанию `Europe/Moscow`), готовность заказа не влияет на попадание в список долгов;
- VK-код действует 15 минут, ищется по HMAC-отпечатку, подтверждается BCrypt и атомарно помечается использованным;
- после пяти неверных попыток VK-пользователь блокируется на 15 минут, endpoint возвращает `429`;
- связь VK ↔ клиент остаётся взаимно однозначной, а привязка, перевязка и отвязка записываются в `sales.client_vk_link_event`;
- история и долги VK-бота всегда определяются по серверной привязке `vk_user_id`, передать произвольный `clientId` в эти операции нельзя.

Integration-тесты покрывают нормализацию и дубликаты клиентов, обязательные поля долга, складское списание, частичную/полную/повторную и конкурентную оплату, границу бизнес-даты, истечение и конкурентное использование VK-кода, защиту от перебора, перевязку, отвязку и изоляцию истории клиентов.

**Следующее продуктовое улучшение:** добавить отдельный отчёт движения дебиторской задолженности за период. Журнал платежей уже содержит необходимые данные; отчёт должен отдельно показывать созданные долги, поступившие платежи и остаток, не смешивая поздние поступления с исторической выручкой закрытой смены.

## 11. Критерии завершения backend-аудита

Проверку можно считать завершённой, когда:

- backend и обе БД разворачиваются с нуля воспроизводимым способом;
- нет незакрытых подтверждённых P0;
- все endpoint внесены в матрицу доступа;
- критические сценарии заказов, оплаты, склада, смен и долгов покрыты integration-тестами;
- ошибки складского списания не могут оставить оплаченный заказ в несогласованном состоянии;
- повторные и параллельные запросы проверены для денежных и складских операций;
- интеграции имеют тесты timeout, retry и некорректного ответа;
- секреты не хранятся в общей конфигурации;
- API использует согласованную валидацию и формат ошибок;
- readiness, liveness, основные метрики и журналирование пригодны для диагностики;
- итоговый реестр содержит приоритет, решение и регрессионный тест для каждой подтверждённой проблемы.

## 12. Ближайшая очередь задач

Если начинать проверку сразу после этого плана, рекомендуемый порядок:

1. Восстановить корректную историю baseline-миграции и проверить пустую БД.
2. Создать Testcontainers-базу и первый smoke test.
3. Автоматически проверить всю security matrix.
4. Закрыть неавторизованный доступ к `/warehouses/**`.
5. Сделать VK API fail-closed при отсутствии токена.
6. Написать integration-тест атомарности создания и оплаты заказа.
7. Проверить параллельные складские списания.
8. Проверить закрытие смены и финансовый итог.
9. Закрепить tax outbox тестами повторной и параллельной обработки.
10. Спроектировать серверную историю выплат сотрудникам вместо `localStorage`.
