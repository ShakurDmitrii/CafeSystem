# Исправления ML и генетического поиска

Дата проверки: 25 сентября 2026 г.

## Область изменений

Сохранены XGBoost и генетический поиск (популяция, отбор, скрещивание, мутации).
Исправлены входные данные, оценка кандидатов и представление результатов.
Новая БД `cafehelp_ai`, байесовская оптимизация и языковые модели в этот этап не входят.

## Данные и обучение

- Java суммирует покупки по блюду, дате, месту и составу. Несколько покупок одного блюда
  за день становятся одной записью, а не несколькими независимыми примерами спроса.
- Продажи включают продукты вложенных заготовок через общий `RecipeExpansionService`.
  Запрос больше не обращается к `FIRSTCOST`, отсутствующему в выборке оптимизированного пути.
- Пустые техкарты пропускаются с сообщением в журнале. Некорректные даты/количества отклоняются.
- Нужны минимум 10 суточных записей и 3 разные даты. Постоянная целевая переменная
  и постоянная обучающая часть отклоняются; существующий модельный файл не заменяется.
- Проверка отделяет последние даты целиком. Словарь признаков проверки обучается только
  на предыдущих датах; после проверки модель переобучается на всём доступном наборе.
- Публикуются MAE, RMSE, допустимый R² и MAE простого прогноза средним значением.
  Неопределённый R² остаётся `null`. Если модель не лучше базового прогноза, выдаётся предупреждение.
- `confidenceScore` остаётся `null`: калиброванная вероятность успеха нового блюда не измерена.
- Обучение использует не более двух вычислительных потоков XGBoost.

Целевая переменная: `daily_quantity_on_sale_days` — порции за день **при наличии продаж**.
Истории доступности меню, отсутствия продуктов и закрытых дней нет, поэтому нулевые продажи
не достраиваются автоматически. Это не безусловный прогноз спроса на каждый календарный день.

## Склад и единицы

- По умолчанию используется основной склад приложения; `warehouseId` возвращается в ингредиенте.
- `costPerUnit` — стоимость базовой единицы `g`, `ml` или `pcs`.
- При положительном остатке: стоимость остатка / количество, `costSource=warehouse_average`.
- При отсутствии остатка: цена карточки / `unitFactor`, `costSource=default_price_no_stock`.
  В результатах явно указывается применение цены по умолчанию.
- При отсутствии цены используется `null`, не выдуманные 10 рублей. Реальная нулевая цена допустима.
- Расходники не включаются в рецептурный пул. Разные продукты с одинаковым нормализованным
  названием не перезаписывают цену друг друга: неоднозначный пул отклоняется.

Генератор формирует строки в граммах. Миллилитры и штуки не считаются граммами без отдельного
перевода массы: такие позиции исключаются с предупреждением. Если они обязательны — запрос
отклоняется. Наличие товара в каталоге само по себе не означает наличие его на складе.

## Оценка рецептов

- Пропорции берутся из медианных потребностей действующих техкарт по каждому ингредиенту.
  Внутренний API допускает явные положительные `constraints.ingredientGrams`.
- Нет известных граммовок — ингредиент не используется; нет пригодного пула — понятная ошибка.
  Произвольное равномерное деление веса между рисом, рыбой и соусом удалено.
- Общий вес — **сырьё с учётом потребностей техкарты**, не гарантированный выход готового блюда.
  Округление до 0,1 г сохраняет сумму весов, а стоимость кандидата равна сумме строк его техкарты.
- Все варианты сравниваются при одной `sellingPrice`. Если она не указана, используется
  медиана положительных цен меню с предупреждением. Если нет ни цены, ни меню, наценка
  остаётся ориентиром цены, но не используется для объявления прогнозной прибыли.
- Исправлена функция оценки: рост себестоимости сам по себе не повышает привлекательность
  кандидата через автоматически увеличенную цену.
- Генерация и оптимизация используют один и тот же расчёт. Обе могут применять совместимую ML-модель.
- Нет совместимой модели или она не знает часть пула — весь запуск оценивается эвристически.
  `salesSource=heuristic`, `predictedSales=null`, `estimatedProfit=null`. Формула популярности
  служит только относительному ранжированию; она не объявляется количеством продаж.
- При выбранной исправной модели `salesSource=ml`. Ошибка её выполнения останавливает запрос,
  а не незаметно подменяет прогноз эвристикой посреди поиска.
- Обязательные ингредиенты, бюджет, маржа и границы сходства не ослабляются незаметно.
  Сохраняются лучшие уникальные кандидаты разных поколений; итог отсортирован по рейтингу.
- `score` — относительный рейтинг внутри запуска, **не вероятность успеха**.

## Интерфейс и контракт

- Появились цена для сравнения и общий вес сырья.
- Неизвестные показатели показываются как «—», не нулём. Неизмеренная уверенность так и обозначена.
- Результаты отмечаются как предварительные и показывают источник оценки и предупреждения.
- Кэш прежних результатов оптимизации не читается новой версией (`v2`).
- Доменные ошибки Python: HTTP 422, `detail.code=ML_INPUT_INVALID`, `detail.message`.
  Java возвращает HTTP 422, `code=PYTHON_INPUT_INVALID` и ограниченное по длине сообщение.
  Непредусмотренные ошибки и сырые детали валидации по-прежнему не раскрываются клиенту.

Обновлять Java, PyModule и frontend нужно совместно: старый Java-клиент считал отсутствие
числовой уверенности ошибкой. Версия транспортной авторизации остаётся `1`; модельные
артефакты старого формата распознаются, но не используются генератором как суточный прогноз.
После обновления требуется переобучение на достаточном наборе данных. Перед выпуском сохранить
резервную копию текущего модельного файла; тесты не должны заменять рабочую модель.

## Проверки

```powershell
# Из PyModule
.\.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider

# Из корня
.\gradlew.bat test --tests 'com.shakur.cafehelp.Service.MlServices.*' --tests 'com.shakur.cafehelp.Controller.MlValidationErrorTest' --tests '*Python*' --console=plain

# Из frontend

```

Проверены агрегация, стоимость остатка, `null`-уверенность, даты проверки, постоянная цель,
отсутствующие цены/единицы/граммовки, обязательные ингредиенты, ограничения сходства,
единый расчёт техкарты и стоимости, отказ модели, обработка ошибок и вывод интерфейса.

Результат локальной проверки: 30 тестов Python, 18 целевых тестов Java и все 10 тестов frontend
прошли. Production-сборка frontend завершилась успешно; YAML спецификации разобран без ошибок.
Это не полная проверка Java-приложения с реальной БД и не проверка установленного EXE.

## Ограничения и последующие работы

- Проверка всего сценария на рабочем Docker-стеке и прежней ошибки обучения 422 остаётся
  обязательной перед выпуском: Docker Engine на момент проверки недоступен.
- Автономный установщик и Docker-образы этим изменением не пересобраны и не развёрнуты.
- Признаки XGBoost пока содержат наличие ингредиентов и календарь, но не граммовки/цену.
  Коммерческий успех совершенно новых блюд на независимых запусках не подтверждён.
- Исторические версии техкарт/цен отсутствуют: старые продажи сопоставляются с текущими
  справочными данными. Их нельзя называть достоверным историческим расчётом себестоимости.
- Пропорции разных техкарт не гарантируют вкус и технологическую совместимость.
  Перед добавлением в рабочее меню необходимы проверка повара и уточнение готового выхода.
- Текущий единичный временной holdout не заменяет проверку на нескольких периодах и
  отдельную проверку на ранее не продававшихся блюдах. Эти этапы требуют достаточных данных.
